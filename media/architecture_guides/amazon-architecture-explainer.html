04 / Follow a real request

What happens when you buy something?

A simplified journey from search to doorstep.

1

Search for a product

The search service finds candidates in its index, ranks them, then enriches results with price, ratings and delivery estimates.

Search index + cache
2

Open the product page

A page-composition layer requests product details, reviews, stock and recommendations in parallel. Slow optional data can be skipped.

Parallel calls + timeouts
3

Add to cart

The cart service stores the shopper's selected items. Cart availability can be prioritized over perfectly fresh data.

Fast, highly available write
4

Validate checkout

Re-check the final price, address, shipping options, tax and inventory before committing the purchase.

Validate before commit
5

Place the order

Reserve inventory, authorize payment, check fraud, save the order and publish an OrderPlaced event.

Idempotency + workflow
6

Trigger background work

The event can notify fulfillment, email, analytics, recommendations and seller systems without blocking the checkout response.

Queue / pub-sub
7

Pick, pack and ship

Systems choose a suitable fulfillment center, coordinate packing and carrier routing, and send tracking updates.

Warehouse + logistics
8

Keep status updated

Shipping events update the order journey; the customer can see confirmation and delivery progress.

Events + notifications
Why idempotency matters: if a customer double-clicks Pay or retries after a network timeout, an idempotency key helps prevent the same payment/order action from being applied twice.
05 / Persistence

Data storage strategy

There isn't one database that is best for every type of data.

NeedTypical storeWhy it fits
Cart / sessionDynamoDB-style key-value NoSQLFast key-based access and high availability at scale.
Orders / transactionsRelational DB such as Aurora / RDS, or fit-for-purpose storesStructured records and transaction guarantees where needed.
Images / media / backupsObject storage such as S3Stores large files separately from application records.
Repeated fast readsIn-memory cache such as Redis / ElastiCacheReduces repeated database work and improves response time.
Product discoverySearch indexSupports text retrieval, filters, facets and ranking.
AnalyticsData lake + warehouseSupports large-scale reporting and model training.
Relationship analysisGraph database such as NeptuneUseful for connected relationships such as fraud networks.

⚖️ Consistency vs availability

✓Browsing / cart: a brief delay in data freshness may be acceptable to keep the experience responsive.
✓Payment / final stock commitment: correctness matters; carefully coordinate writes to avoid double charges or overselling.

🔁 Distributed data basics

✓Replication: keep copies to survive failures.
✓Partitioning: split data across nodes to handle growth.
✓Eventual consistency: replicas may briefly differ, then converge.
06 / Asynchronous work

One event, many consumers

After an order is saved, independent systems can react to the same event.

🧾 Order ServiceSave order + publish OrderPlaced
⟶
📦 FulfillmentChoose warehouse, pick and pack
✉️ NotificationsSend order confirmation
📊 AnalyticsUpdate sales reporting
🛡️ Fraud / Seller systemsCheck risk and notify seller
📬

SQS — queue

One task at a time per consumer

Buffers work so a worker can process tasks at a safe pace.

📣

SNS — publish / subscribe

One event, multiple subscribers

Fans a notification out to multiple independent destinations.

〰️

Kinesis / streams

Continuous event data

Supports streaming activity such as click events and analytics pipelines.

Important patterns: consumers should handle duplicate messages safely (idempotency); retries and dead-letter queues help isolate persistent failures. An outbox pattern can keep a database change and its event publication in sync.
07 / Growth and failure

How the system scales and stays available

Scale horizontally, cache aggressively, and assume dependencies can fail.

📈 Scalability toolkit

✓Horizontal scaling: add more instances rather than relying on one bigger server.
✓Stateless services: any healthy instance can handle a request.
✓Multi-level caching: browser → CDN → service cache → database.
✓Sharding / replicas: distribute data and read load.
✓Queues + backpressure: buffer work and protect overloaded services.
✓Precomputation: prepare recommendations and rankings before a request.

🛡️ Reliability toolkit

✓Timeouts: don't wait forever on a slow dependency.
✓Retries + backoff: retry carefully without causing a traffic storm.
✓Circuit breaker: pause calls to a failing service and recover later.
✓Graceful degradation: show the product page even if optional reviews fail.
✓Multi-AZ / cells: isolate failures and limit how many users are affected.
✓Health checks: stop sending traffic to unhealthy instances.

A simple caching path

🌐 Browser cacheReuse assets already downloaded
🌍 CDN cacheServe content near the customer
⚡ Service cacheReuse common, frequently requested data

🔥 Prime Day / Black Friday readiness

✓Forecast demand and pre-scale capacity.
✓Warm caches and load-test critical paths.
✓Buffer background work in queues.
✓Throttle excess traffic and protect checkout.
✓Disable non-essential features if needed.

📉 When a dependency is slow

1Set a timeout so the request has a limit.
2Use a cached or default response when safe.
3Skip optional content to keep the page usable.
4Measure the failure and alert the owning team.
09 / Revision

System design interview cheat sheet

A clear order to explain your design without getting lost in details.

🧭 Explain the design in this order

  1. Clarify features: browse, search, cart, pay, track, reviews.
  2. Estimate users, request rate, storage and read/write ratio.
  3. Draw client → CDN → load balancer → API → services → data.
  4. Deep-dive into cart, orders, payment, inventory and search.
  5. Explain scaling, caching, queues, replication and failure handling.
  6. Discuss trade-offs: consistency, latency, freshness and cost.

🎯 Remember these principles

  1. Microservices have clear APIs and ownership.
  2. Choose a data store to fit each service's needs.
  3. Use asynchronous events for work that doesn't need an immediate response.
  4. Protect critical actions with idempotency and workflow coordination.
  5. Expect failures: timeouts, retries, circuit breakers and fallbacks.
  6. Measure p99 latency, errors and throughput.
